# Router merge: `SynapseRouter` + `EnhancedSynapseRouter` → one type; `MultiTransportRouter` stays a layer

**Status: DESIGN NOTE — report before code, per the PM/CireSnave's explicit instruction. No implementation, no PR.**

**CireSnave's ruling, verbatim as relayed:** the router types merge into one with the capabilities of all three, unless there is a reason they need to be separate. Measured below: there is a reason for exactly one of the three (`MultiTransportRouter`). This is a two-way merge (`SynapseRouter` + `EnhancedSynapseRouter`), not three.

All claims below were independently verified against the actual source in this worktree (`C:/Users/.../email-transport-impl`, `feat/email-transport` branch — the router files are unchanged from `origin/main` on this branch, so the read applies equally there) before being written down, not taken from the PM's message.

## 1. Why `MultiTransportRouter` stays separate

Confirmed by direct read of `src/transport/router.rs`:

- `send_message(&self, target: &str, message: &SecureMessage, urgency: MessageUrgency) -> Result<DeliveryReceipt>` takes an **already-built, already-signed** `SecureMessage`. It routes; it does not construct or sign.
- Holds `tcp`/`mdns`/`nat`/`email: Option<Arc<dyn Transport>>`, a `TransportSelector`, and a route cache — transport-selection state, not identity state.
- `grep -c "CryptoManager\|IdentityRegistry" src/transport/router.rs` → **0**. Positive control: the same query against `src/router.rs` → **6**, confirming the query finds these types where they exist and isn't just failing silently.
- `new_with_provider(config, our_entity_id, provider: Box<dyn TransportProvider>)` is the injection seam `ProductionTransportProvider` plugs into — this is what the email-transport work (Task 1 of the just-merged slice, PR #55) repaired, wiring `EmailTransportImpl` into `create_email_transport`. Collapsing `MultiTransportRouter` into the merged router would fuse "which pipe do I use" with "how do I sign a message" and destroy this seam.

**Conclusion: `MultiTransportRouter` is a layer the merged router composes, not a peer to merge with it.**

## 2. The merged type's full API, collisions named

`SynapseRouter`'s public API (`src/router.rs`): `new(config, our_global_id)`, `send_message(simple_msg, destination_global_id)`, `receive_messages()`, `register_peer_key(global_id, pem)`, `generate_keypair()`, `get_our_global_id()`, `get_health()`, `convert_to_secure_message(...)`, `start()`, `stop()`, `status() -> String`, `register_entity(...)`, `add_entity_key(global_id, key)`.

`EnhancedSynapseRouter`'s public API (`src/router_enhanced.rs`): `new(config, our_global_id)`, `send_message_smart(to, content, type, level, urgency)`, `send_message_with_transport(...)`, `test_connection(target)`, `start()`, `status() -> EnhancedRouterStatus`, `benchmark_transport(target)`, `email_server()`, `is_running_email_server()`, `email_server_connectivity()`.

**Named collisions and which body survives:**

| Method | Collision | Resolution |
|---|---|---|
| `new(config, our_global_id)` | Identical signature on both | One constructor. It must build everything both did: crypto manager, identity registry, the (now-singular) email path, and — new — the `MultiTransportRouter` that `EnhancedSynapseRouter` previously held as `Option<Arc<MultiTransportRouter>>`. Keep it optional (a router with no transports configured is still a valid, email-only router) rather than forcing multi-transport setup on every caller. |
| `start()` | Present on both, `EnhancedSynapseRouter`'s calls `self.synapse_router.start()` **but that call is commented out** (`router_enhanced.rs:619`) | `SynapseRouter::start()`'s body survives (whatever it actually does — verify at implementation time; the point is Enhanced's version is presently a no-op for this half). Un-comment the inner call rather than leaving it dead. |
| `status()` | **Different return types**: `SynapseRouter::status() -> String`, `EnhancedSynapseRouter::status() -> EnhancedRouterStatus` | Not a true collision once you look at the types — `EnhancedRouterStatus` is the richer one (it already exists as a superset-shaped struct). The merged type keeps `status() -> EnhancedRouterStatus`; if any consumer destructured the plain `String` form, that call site updates to read the richer struct's relevant field (name every such call site at implementation time — this doc's §5 lists the consumer files, not each individual call). |

Everything else is additive, no collision: `receive_messages`, `register_peer_key`, `generate_keypair`, `convert_to_secure_message`, `stop`, `register_entity`, `add_entity_key` (from `SynapseRouter`) all become real methods on the merged type, since nothing on `EnhancedSynapseRouter` conflicts with them. `send_message_smart`, `send_message_with_transport`, `test_connection`, `benchmark_transport`, `email_server`, `is_running_email_server`, `email_server_connectivity` (from `EnhancedSynapseRouter`) likewise carry over untouched in name and signature.

**Plain `send_message` is genuinely absent from `EnhancedSynapseRouter` and must be decided, not silently inherited:** `SynapseRouter::send_message(simple_msg, destination)` is the low-level, single-transport (email-only) send. The merged type should keep this name for exactly that behavior (email-only, no transport selection) and use `send_message_smart`/`send_message_with_transport` for the multi-transport-aware paths, matching what a caller who wants "just send this over email" versus "send this as fast as possible" would each reach for. Do not have one `send_message` silently pick a transport a caller didn't ask for.

## 3. Fixing the email wire-format defect once — and a third defect found while verifying this

**The prize, stated precisely:** today, `EnhancedSynapseRouter::send_message_smart`'s email fallback (`router_enhanced.rs:517-534`, reached whenever `MultiTransportRouter` is absent, urgency is low, or the multi-transport send fails) calls `self.synapse_router.send_message(simple_msg, ...)` — `SynapseRouter`'s own method, which serializes the whole signed `SecureMessage` as JSON (`router.rs:93`, this part is honest) and hands it to `src/email.rs`'s `EmailTransport::send_message`. **That function is the confirmed 4th wire-format-hand-picking instance** (named out of scope in PR #55): it ignores that its input is already a full signed `SecureMessage` and rebuilds a throwaway one around it with `sender_proof` forced back to `SenderProof::unsigned()` (`email.rs:62-73`), then base64-encodes only that wrapper's `encrypted_content` into the email body (`email.rs:107`) — discarding the original signature, metadata, and routing path.

So "use the fixed router" (`EnhancedSynapseRouter`, the documented main interface) **does not currently avoid this defect**, because its own fallback reaches it via `SynapseRouter`.

**Fix, once:** the merged router's email path must be `EmailTransportImpl` (from PR #55, real `Transport`/`TransportReceive` implementation, already fixed to serialize the whole `SecureMessage` as JSON both directions) — not `src/email.rs`'s `EmailTransport`, and not through `SimpleMessage`'s round-trip-through-JSON-string indirection `SynapseRouter::send_message` currently uses (`router.rs:93`: `content: serde_json::to_string(&secure_msg)?` stuffed into a `SimpleMessage.content` field, then unpacked again on the far side — a working but needlessly indirect path that only exists because `email.rs::EmailTransport` predates the `Transport` trait). The merged router's email-only `send_message` should construct a `SecureMessage`, sign it, and hand it directly to an `EmailTransportImpl` instance's `send_message` — one signing call, one serialization, one wire format, matching every other transport in this crate.

**A third defect, found independently while verifying this design, not on the PM's original list:** `EnhancedSynapseRouter::create_secure_message` (`router_enhanced.rs:661-682`, private, used by `send_message_smart`'s `MultiTransportRouter` fast-path — the path taken for `RealTime`/`Interactive` urgency, i.e. the path most likely to actually be used in latency-sensitive traffic) **hardcodes `sender_proof: SenderProof::unsigned()` and never calls the crypto manager at all.** Its own comment: `// For now, create a basic secure message // In a real implementation, this would involve the crypto manager`. This means **the fast path is unsigned and the slow (email fallback) path is signed** — the exact opposite of what a caller choosing "urgent" would expect, and worse than either path being consistently one way. **The merged router's `MultiTransportRouter`-backed send path must sign the message the same way the email path does, using one shared `sign_secure_message` call, not two divergent constructors that happen to both produce a `SecureMessage`.**

## 4. The unverified receive path: state a disposition, don't let it survive by inheritance

`SynapseRouter::receive_messages()` → `process_email_message()` (`router.rs:136-171`) parses the body back with `serde_json::from_str::<SecureMessage>` but calls **zero signature verification** anywhere in its body — self-documented at `router.rs:104-105,133-135` ("Unverified: senders are not authenticated on this path... this path has no trust store"). It only attempts `crypto_manager.open_payload` (sealing/decryption), then returns the message as delivered regardless of what `sender_proof` says.

**Currently non-exploitable in practice**, because `src/email.rs`'s `receive_messages()`/`receive_messages_imap()` are both permanent stubs that unconditionally return `Ok(Vec::new())` — so `SynapseRouter::receive_messages()` always returns empty today, and the shipped `synapse-client listen` command runs and logs nothing, forever.

**Three options, and this design note's recommendation:**
1. **Delete it.** The merged router's receive path becomes `EmailTransportImpl::receive_raw` plus `TransportManager`'s existing signature verification (the same path every other transport already uses) — the unverified `process_email_message`/`SynapseEmailMessage` machinery in `src/email.rs` and `src/router.rs` is deleted outright, not deprecated.
2. **Fix it in place** — wire real `TrustStore`/`sender_auth` verification into `process_email_message`. Rejected as the recommendation: this duplicates verification logic `TransportManager` already owns, for a path that's being replaced anyway per §3.
3. **Keep it, unauthenticated, documented louder.** Rejected: shipping a receive path that silently accepts unsigned/forged senders, in a crate whose transport contract's entire point is honest, verified delivery, is precisely the kind of gap this portfolio's recent work (the wire-format sweep, the metrics-honesty contract) exists to close, not preserve.

**Recommendation: option 1.** Once `EmailTransportImpl` carries both directions (per §3), there is no reason for a second, unverified, hand-rolled receive path to exist alongside it. **Do not let it survive the merge by simply relocating it onto the merged type's namespace** — that would be "keep it" wearing a new struct name.

## 5. Naming: should `MultiTransportRouter` stop being re-exported at the top level?

CireSnave's observation, independently confirmed: `lib.rs:245-247` re-exports `SynapseRouter`, `EnhancedSynapseRouter`, and (via `pub use transport::router::MultiTransportRouter` or equivalent — confirm exact export path at implementation time) `MultiTransportRouter`, presenting three `*Router` types as siblings, all three with a `new(config, id)`-shaped constructor and a `send_message`-shaped method. That surface is confusing regardless of whether the layering underneath is sound (§1 establishes that it is).

**Recommendation: yes, stop re-exporting `MultiTransportRouter` from the crate root.** It remains `pub` within `src/transport/` (an internal implementation detail the merged router composes via `new_with_provider`), but a normal consumer of this crate should see one router type at the top level, not three. If any in-tree consumer constructs a `MultiTransportRouter` directly today (check at implementation time — this note did not find one outside `router_enhanced.rs` itself and its own tests), that call site needs the merged router's constructor instead, or an explicit lower-level escape hatch (`crate::transport::router::MultiTransportRouter`) if direct access is still needed for some reason.

## 6. Migration: every in-tree consumer, named

Confirmed by `grep -rln "SynapseRouter" --include=*.rs .` (excluding `src/router.rs`/`src/lib.rs`, the definition/re-export sites) at this worktree:

- **`src/bin/router.rs`** — the shipped `synapse-router` CLI binary. Constructs `SynapseRouter::new`, calls `.send_message(...)` (real `send_test_message`), `.get_our_global_id()`, `.get_health()`/status-style checks, `.start()`. **Breaks**: needs to switch to the merged type's constructor; `send_test_message` should likely move to whichever `send_message`/`send_message_smart` the CLI's own semantics call for (a one-shot test send probably wants the plain, non-multi-transport `send_message`, per §2's naming resolution).
- **`src/bin/client.rs`** — the shipped `synapse-client` CLI binary. Constructs `SynapseRouter::new` (aliased as `client`), calls `.start()`, `.receive_messages()` (`listen_for_messages` — **this call currently does nothing, per §4**, and after the merge/receive-path decision, either starts actually receiving real mail or the `listen` subcommand needs its own disposition decided), `.send_message(...)` (via `send_message`), identity/connectivity commands. **Breaks**: constructor, and `listen`'s behavior changes meaningfully once §4's fix lands (from "runs forever and logs nothing" to "actually receives," which is a behavior change worth calling out in the eventual PR, not just a signature change).
- **~9 examples** (`examples/ai_assistant_network.rs`, `ai_assistant_stub.rs`, `basic_chat.rs`, `email_integration_test.rs`, `enhanced_router_demo.rs`, `enterprise_service_mesh.rs`, `multi_modal_collaboration.rs`, `simple_unknown_name_resolution.rs`, `tool_interaction.rs`, plus `unified_transport_demo.rs` which references `EnhancedSynapseRouter`) — construct one or the other router type; most (per `lib.rs`'s own doc examples using `EnhancedSynapseRouter`) already lean toward the richer API, so migration is likely closer to a rename than a rewrite for these, but each needs an individual pass to confirm no `SynapseRouter`-only method (`receive_messages`, `register_peer_key`, etc.) is being called on what was previously an `EnhancedSynapseRouter` reference expecting it to be absent, or vice versa.
- **Integration tests** (`tests/basic_integration_test.rs`, `concurrent_registry_access_test.rs`, `edge_case_test.rs`, `high_load_test.rs`, `multi_transport_integration.rs`, `sealing.rs`, plus `agent_certificates.rs`, `protocol_version.rs`, `receiver_acknowledgement.rs`, `replay_suppression.rs`, `sender_authentication.rs`, `tcp_delivery_probe.rs`, `transport_repairs.rs` per the broader `receive_messages`/`SynapseRouter::new` grep) — each needs checking for which router type it constructs and whether it depends on a method only one side had.
- **`src/connectivity.rs`, `src/streaming.rs`, `src/mcp_server.rs`** — reference `SynapseRouter` per the earlier grep; each needs a pass to confirm what it actually calls.

**This is 2.0.0 work and it is breaking, stated plainly rather than minimized:** every one of the above call sites changes at least its constructor, several change their receive-path behavior meaningfully (not just a rename), and the top-level export surface shrinks from three router types to one (plus `MultiTransportRouter` demoted to an internal path, per §5). No attempt should be made to preserve source compatibility for `SynapseRouter`/`EnhancedSynapseRouter` as separate names (e.g. via a type alias) — that would just be the naming confusion CireSnave flagged, wearing a deprecation notice instead of a fix.

## Open questions for the implementation plan (not this note)

- Exact new type name (`SynapseRouter`? Something else, given `EnhancedSynapseRouter`'s capabilities are now the baseline, not an enhancement over it?) — a naming decision, not an architecture one; deferred to plan time.
- Whether `MultiTransportRouter` should be constructed unconditionally by the merged router's `new()` (always-on, `email`-only when no other transport is configured) or remain the `Option<Arc<...>>` `EnhancedSynapseRouter` used — this note recommends keeping it optional (§2) but the plan should confirm this against how `ProductionTransportProvider`'s defaults behave when no transports are configured at all.
- The exact `EnhancedRouterStatus`/`String` status field mapping for any consumer that pattern-matched the old plain-string `status()` — needs enumerating call sites, not designing in the abstract.
