# Fetch scan: make `fetch` cost independent of the leased prefix

From the synapse lane, 2026-10-09. PM order 3 (after the depth-scan harness), to land before the M9
soak. Evidence: `origin/main` `dd18922` (6.0.0-rc.26); numbers are from the PM-accepted depth-scan run
at `e1468f7` on this laptop (1 KiB bodies, 10 000 messages per role, half leased, 100 samples):
`fetch(max=1)` past the leased half, p50 46 ms, p99 63 ms. Re-take with
`cargo test --release --features mailbox-redb --test mailbox_depth_cost -- --ignored --nocapture`.

## The problem

`RedbTxn::scan_free` walks the role's `META` rows from `seq` 0 and JSON-decodes every row to read its
lease, then skips the ones that are not free. Bodies are already skipped. So `fetch(max=1)` costs
O(messages ahead of the first free one), all under the mailbox mutex and inside a redb write
transaction. M7 polls `fetch` at 1 Hz per session; 20 sessions is up to ~1 s of mutex time per second
only if every lane sits at 10 000 messages. Real mailboxes are small, so this is a ceiling fix, not a
fire.

## Not yet known (first step of the plan, before any change)

Where the 46 ms goes: JSON decode, redb range iteration, or the write-transaction commit. The plan's
first task profiles the three on the existing test and records the split in the PR. The design below
is the recommendation only if decode dominates; if iteration or commit dominates, I stop and ask.

## Design (recommended)

A new redb table `HELD: (role, seq) -> (epoch: u64, until_micros: i64)`, fixed-width values, no JSON.
- `put` inserts or updates the row when the message has a lease, and removes it when it has none.
- `remove` (ack, retention drop, dead-letter) removes the row.
- `scan_free` becomes: iterate `META` keys in `seq` order; for each seq, look at `HELD`. A seq with no
  `HELD` row is free without decoding its JSON; a seq with a row is free iff
  `epoch < current epoch || until <= now`, again with no JSON. Only a free message's `META` row is
  decoded (to build the `Stored`). The visit order, early stop and results are unchanged.
- Cost drops from one JSON decode per skipped row to one fixed-width compare. Still O(rows) iteration,
  but of small values. If the profile says iteration itself is the cost, see the alternative.

**Migration.** An existing database has no `HELD`. On `RedbStore::open`, if a `meta_version` counter is
absent or lower, one write transaction rebuilds `HELD` from `META` and sets the counter. A database
written by a newer binary and opened by an older one is not supported: rc.26 and earlier do not read
the counter, so they would update `META` and leave `HELD` stale, and a later new binary would then
trust the stale rows. The counter protects only a *new* binary from a *newer* format; nothing stops an
old binary. The CHANGELOG says so (Breaking: no downgrade). (Corrected 2026-10-09: the first draft
claimed the counter makes an older binary refuse; it cannot.) This is the one irreversible part.

**Alternative (smaller, no migration):** cache, per role in memory, the lowest `seq` that might be free
(`first_free_hint`), advanced by `scan_free` and lowered by `ack`/lease-expiry events. Rejected as the
default: lease expiry is time-based and writes nothing, so the hint needs a timer or a conservative
reset every `max_lease`, and it is lost at restart (one slow fetch after each start).

## Tests (red first)

1. Correctness oracle: a randomized sequence of enqueue, fetch, ack, claim-takeover and time advance runs
   against `MemoryStore` and `RedbStore`; every `fetch` result and `depths` must be identical.
2. `HELD` consistency: after any sequence, `HELD` rows == `META` rows with a lease (checked through a
   test-only accessor).
3. Migration: a database built by the rc.26 code (fixture generated by the old binary's layout, checked
   in or constructed through the old table set) opens, rebuilds `HELD`, and fetches correctly.
4. A database stamped with a newer format than the binary knows is refused with a clear error.
5. The existing `mailbox_depth_cost` measurement is extended with the post-change `fetch` numbers.
   Pass bar: `fetch(max=1)` past a leased half no longer grows with the leased count (p50 within 2x of
   the empty-leased case), not an absolute number.
6. Sabotage check: drop the `HELD` update in `put`; test 2 must fail.

## Not in scope

A `wait_secs` long-poll on `/v1/fetch` (plan D: only if measured to matter). `depths` (S-1) is already
META-only and is not changed. The protocol and the HTTP API are unchanged.

## Size and version

One PR, about 1 day: profile 0.1 d, design and tests 0.6 d, migration 0.3 d. Behaviour is unchanged and
the on-disk format gains a table, so I treat it as non-breaking for callers, but the database cannot be
downgraded: the PM allocates the number (expected 6.0.0-rc.27) and decides whether that needs a Breaking
note.

## Decisions for the PM

1. Approve the `HELD` table with a one-time migration (recommended), or prefer the in-memory hint.
2. Is "cannot downgrade the database file" acceptable for a pre-release line? (No deployed 6.x database
   outside CireSnave's lanes that I know of.)
3. Pass bar: relative (above) rather than an absolute millisecond figure.

## PM rulings (2026-10-09 06:54Z)

1. Design A (`HELD` table + one-time migration), **only after** the step-1 profile shows JSON decode of
   `META` rows dominates; otherwise stop and ask.
2. A one-way database format change is allowed on the rc line, as 6.0.0-rc.27 with a **Breaking**
   CHANGELOG entry, provided the migration is:
   - **one redb write transaction** (all-or-nothing, crash-safe);
   - **idempotent**;
   - **refuses a newer-than-known format** with a clear error;
   - covered by a test that kills the process mid-migration (or simulates it) and reopens.
3. Pass bar is relative (above). The PR also records the measured `fetch(max=1)` p50 at 5k leased,
   before and after.
4. This spec lands first as a docs-only PR; **rc.27 rides the implementation PR**, not this one.
